# Reproducible benchmark results

These are **measured runs**, generated by `backend/app.cli benchmark`. They are
not encoded as expected constants in tests. Raw JSON (including every metric,
solver status, objective value, bound and runtime) is checked in beside this
report:

- [`medium.json`](benchmarks/medium.json)
- [`large.json`](benchmarks/large.json)

## Reproducing a run

From the repository root:

```bash
cd backend
python -m app.cli benchmark --scale medium --time-limit 900 --deterministic-time 30 \
    --workers 1 --output ../docs/benchmarks/medium.json
python -m app.cli benchmark --scale large --time-limit 900 --deterministic-time 30 \
    --workers 1 --output ../docs/benchmarks/large.json
```

Two settings make the result **identical on every machine**:

| Setting | Value | Why |
| --- | --- | --- |
| Planning reference | `2024-05-13T00:00:00Z` | The demo factory, the planning horizon and the disruption events all use this instant, so the *instance* is fixed. The CLI prints the reference it used and writes it to the raw JSON. |
| Deterministic budget | `--deterministic-time 30` | The solver counts its **internal work** instead of elapsed time, so it performs the same search on a slow laptop and on a fast server. |
| Search workers | `--workers 1` | A single worker makes the search itself deterministic. |

The data seed is `20240517`. The raw JSON also contains the UTC `generated_at`
value, the horizon, the solver status, the objective value and the best bound.

Without a deterministic budget a wall-clock-limited run is *not* reproducible:
a faster host simply finds more improving solutions in the same number of
seconds. That is a property of time-limited search, not of this platform, and
the platform never claims otherwise — `FEASIBLE` means "a valid plan was
found", not "this is the best plan".

| Demo seed | 20240517 |

| Random seed | 42 |
| Objective | `weighted_tardiness` (default weights) |
| Warm start | The FCFS baseline is added as a **complete** CP-SAT hint. |
| Validator | Independent H1–H14 audit, run on *both* plans. |
| Status | Both plans were `FEASIBLE` and passed the validator with 0 violations. The optimiser did **not** prove global optimality within the budget. |

The host for this run had 20 logical CPUs and approximately 15.6 GiB RAM, but
the search itself used a single worker, so the CPU count does not influence the
result. Do not infer production throughput from this single measurement.

## Medium comparison (94 operations)

| Metric | FCFS | CP-SAT | Change | Result |
| --- | ---: | ---: | ---: | --- |
| On-time delivery | 85.00% | 90.00% | +5.00 percentage points | Better |
| Weighted tardiness | 16,891 min | 6,550 min | −61.22% | Better |
| Tardiness | 6,261 min | 1,535 min | −75.48% | Better |
| Makespan | 10,140 min | 10,520 min | +3.75% | **Worse** |
| Setup | 930 min | 435 min | −53.23% | Better |
| Operating cost | 15,267.95 | 15,231.72 | −0.24% | Better |
| Penalty cost | 7,037.92 | 2,729.17 | −61.22% | Better |
| Overtime | 0 min | 0 min | 0 | Equal |
| Machine utilisation | 6.03% | 6.03% | 0 | Equal |

5 metrics improved, 2 regressed, 3 equal. CP-SAT objective value:
**6,704,175**; best bound: **4,611,970**. The solution is labelled `FEASIBLE`;
the non-zero bound gap means it is not represented as proven optimal.

The makespan regression is real and is reported rather than hidden: the
optimiser buys a large tardiness reduction by starting some operations later
than the greedy baseline does. A planner who prefers a shorter plan can select
the `minimize_makespan` objective instead.

5 metrics improved, 2 regressed, 3 equal. CP-SAT objective value:

The large run improved delivery and tardiness but regressed on makespan and on
setup time. The comparison reports those regressions rather than claiming the
candidate was better on every metric. It was still a validated `FEASIBLE` plan,
not a proven optimum.

### Why the large instance is harder

The large dataset scales the plant to 22 machines and 20 operators, so each
machine has up to 80 candidate operations. The sequence-dependent setup model
needs one successor literal per ordered candidate pair, which makes the model
quadratic in that number (≈ 49 000 variables and ≈ 87 000 clauses in total).
Two consequences are visible in the numbers above:

* the first incumbent is found after roughly 15 s of search, so a short
  wall-clock limit can end the run with *no* solution at all (status
  `UNKNOWN`);
* the setup term is dropped from the objective on the machines that fall back
  to the pairwise setup model, so the optimiser is less inclined to reduce
  changeovers. This is reported as an `setup_pairwise_fallback` diagnostic
  rather than being silently applied.

The platform mitigates the first effect automatically: CP-SAT's expensive
*probing* presolve is switched off for models above 20 000 variables, because
on these sequencing models it consumes more time than the whole search.

## Interpretation and limitations

* The weighted objective favours lower weighted tardiness; it does not imply
  that every metric improves. Both runs are concrete counterexamples.
* These results belong to the seeded demo factory, the planning reference in
  the raw JSON, the given objective weights and the stated deterministic
  budget. They are not a service-level guarantee for a real factory.
* The medium instance uses one 11-machine / 10-operator cell. The large
  instance scales the plant to 22 machines / 20 operators as well as scaling
  demand and materials, so it tests a larger feasible plant rather than
  manufacturing an infeasible overload.
* `FEASIBLE` never means "proven optimal". Only `OPTIMAL` does, and neither
  run reached it: the best bound is far below the objective value, so a better
  plan very likely exists.
* The measured improvements are **not** a claim about a real factory. A real
  deployment has to be calibrated on its own data, and the baseline is the
  honest yardstick.
